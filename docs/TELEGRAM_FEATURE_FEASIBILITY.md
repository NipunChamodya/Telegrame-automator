# Installed API and advanced-feature feasibility audit

Audit: 2026-10-28, Telethon 1.45.0, generated Telegram layer **229**, inspected locally via public constructors without account/network access. Online Telegram documentation can describe methods newer than a package. A generated constructor is evidence of signaling/API availability, **not a working user feature**. App status below is the V3 research baseline; implementation evidence is recorded separately after milestone tests.

| Requested feature | Installed API evidence | Integration assessment / baseline app status |
| --- | --- | --- |
| Voice calls | `phone.RequestCallRequest` | Signaling exists; no audio transport, cryptographic call lifecycle, microphone pipeline or native controls. Unsupported; separate media-engine/security project. [Official calls](https://core.telegram.org/api/calls). |
| Video calls | Same call family and protocol parameters | Requires actual video/audio media stack, camera permissions and lifecycle beyond a raw RPC. Unsupported. |
| Group calls | `phone.JoinGroupCallRequest` | Signaling is not a mixer/WebRTC implementation; no working group media engine. Unsupported. [Group calls](https://core.telegram.org/api/group-calls). |
| Stories | `stories.GetPeerStoriesRequest` | Fetch primitives exist; privacy, expiry, views, media and publishing are not implemented. Unsupported. [Stories](https://core.telegram.org/api/stories). |
| Secret Chats | `messages.RequestEncryptionRequest` | A signaling type does not implement the separate secret-chat schema, key verification, sequencing, forward secrecy or lifetime handling. Existing cloud sessions are not secret-chat sessions. Not planned in this increment; no homemade crypto. [Secret chats](https://core.telegram.org/api/end-to-end). |
| Polls | `messages.SendVoteRequest` | Raw vote method exists; rendering/questions/results and intentional voting need their own typed model/tests. Unsupported interaction; do not invent buttons or reveal anonymous voters. |
| Reactions | `messages.SendReactionRequest` | Can normalize server-provided reaction/count metadata; sending/retracting and paid/custom reactions need explicit capability/cost handling. No paid operation or fake animation. [Reactions](https://core.telegram.org/api/reactions). |
| Stickers | `messages.GetAllStickersRequest` | Catalog methods exist; document retrieval, formats, dimensions, protection and renderer are additional work. Unsupported playback. |
| Animated emoji | `messages.GetEmojiStickersRequest` | Custom emoji/animation assets and entitlement-aware renderers are not supplied by text APIs. Unsupported playback. |
| Scheduled messages | `messages.GetScheduledHistoryRequest` | Schedule/history primitives exist; separate queue, cancellation and exact future-destination approval are missing. Unsupported; never turn an ordinary confirmed send into a schedule implicitly. [Scheduling](https://core.telegram.org/api/scheduled-messages). |
| Message editing | `messages.EditMessageRequest` | Feasible for scoped own plain-text messages with fresh ownership checks, exact preview and uncertain-outcome ledger. Not implemented at baseline. Captions/inline/bot/business edits require further semantics. |
| Message deletion | `messages.DeleteMessagesRequest`; public client helper | Feasible only after verifying the returned message belongs to the chosen peer and account; one explicit target, no bulk deletion. Channel semantics differ. Not implemented at baseline. |
| Forwarding | `messages.ForwardMessagesRequest` | Feasible with protected-content and exact destination checks; requires source attribution, random IDs and persistent uncertainty protections. Unsupported in this increment unless separately tested; no multi-destination fanout. |
| Pins | `messages.UpdatePinnedMessageRequest` | Mutation must use current permissions and notify semantics. Displaying a server `pinned` flag is not managing the whole pin list. Unsupported mutation. |
| Topics / forums | **`messages.GetForumTopicsRequest` exists; guessed `channels.GetForumTopicsRequest` does not** | Current layer's namespace was verified rather than assumed. Thread-root routing/drafts/permissions remain missing; managed sending to forums remains blocked. [Threads](https://core.telegram.org/api/threads). |
| Telegram Premium | `help.GetPremiumPromoRequest` | Entitlement metadata does not implement purchasing, limits or premium UI. No purchase/Stars/flood-skip workflow. Unsupported management. [Premium](https://core.telegram.org/api/premium). |
| Telegram Business | `account.UpdateBusinessGreetingMessageRequest`; guessed getter absent | Business details are exposed through relevant full-user/schema fields and other methods; one absent getter does not prove all API support absent. Connected-bot/quick-reply/greeting/payment lifecycles are not implemented. [Business](https://core.telegram.org/api/business). |
| Contacts/profile data | `contacts.GetContactsRequest`, `users.GetFullUserRequest`, group/channel full methods | Feasible as explicit bounded reads, cache by verified account/peer; avoid returning phone numbers/session/access-hash fields by default. No per-row full-profile requests. |
| Telegram folders | `messages.GetDialogFiltersRequest` | Read-only folder metadata is feasible. Remote modification and matching rules require more than local labels; do not present app-only views as synchronized Telegram folders. [Folder semantics](https://core.telegram.org/api/folders). |
| Sponsored messages | `messages.GetSponsoredMessagesRequest`, view/click requests | Schema exists, but compliant presentation/impression/click/report/media lifecycle does not. Channel/bot reading must remain gated until complete; empty/unknown response cannot be fabricated. [Specification](https://core.telegram.org/api/sponsored-messages). |

## Architecture choice

Keep Telethon and its existing authorization files for tested incremental cloud messaging. TDLib can provide a broader client-state abstraction, but a migration would introduce a new authorization/storage/key/build lifecycle; no supported drop-in session conversion was established. Hybrid engines would increase consistency and security complexity. See [CLIENT_ARCHITECTURE_DECISION.md](CLIENT_ARCHITECTURE_DECISION.md).

Capabilities must be returned by Python and consumed by native controls. Unsupported content/actions remain explicitly unavailable. No feature is marked production-ready because its constructor exists, and no live Telegram call or message mutation was performed during this audit.
