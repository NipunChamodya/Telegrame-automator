# Telegram reference study and capability matrix

Research date: 2026-10-28. The primary matrix records the V3 Phase 1/2 pre-implementation baseline; the M2/M3/M4 deltas below record the implemented subset. It is not a full-parity claim, a legal opinion, or evidence that this application passed live Telegram acceptance tests. No account login, message submission, or private Telegram data was used during this study. Candidate APIs below require the separate installed-Telethon/schema audit before implementation.

## Licensing and platform requirements

The linked licenses identify [WebK as GPLv3](https://github.com/morethanwords/tweb/blob/master/LICENSE), [WebA as GPLv3](https://github.com/Ajaxy/telegram-tt/blob/master/LICENSE), [Telegram Desktop as GPLv3 with its stated exceptions](https://github.com/telegramdesktop/tdesktop/blob/dev/LICENSE), and [native macOS as GPLv2](https://github.com/TelegramMessenger/telegram-macos/blob/master/LICENSE). This study copies no implementation, artwork or source snippets. Describing interaction patterns does not assign this repository a license. Any future source/assets reuse requires a separate provenance and licensing review; do not assume repository-wide licenses cover every dependency or resource.

Platform requirements, paraphrased from [Telegram API Terms](https://core.telegram.org/api/terms): use this application's own API credentials, identify its Telegram API use, and make unofficial status clear. A title containing Telegram requires the Unofficial prefix, and the official logo must not be used. Preserve ordinary privacy, read/typing/presence and disappearing-content behavior; do not perform actions without informed consent or create a ghost mode. Access to channel content requires official sponsored-message support. Telegram-derived data must not be harvested for AI/ML development. These constraints are implementation gates, not optional cosmetic polish.

The [application-registration guide](https://core.telegram.org/api/obtaining_api_id) explains obtaining credentials through the developer portal and warns against abusive API use. It does not authorize unsolicited messaging. This application must continue to preserve explicit destination approval, fresh eligibility checks, cooldowns and its persistent delivery ledger.

## How to read the matrix

Statuses describe this repository at the research baseline:

- **Supported:** the narrowly stated local capability exists and has relevant automated tests; this never implies live or visual acceptance.
- **Partial:** an implemented subset exists, with concrete gaps listed.
- **Unsupported:** no end-to-end implementation exists.
- **Investigate:** behavior, API/schema compatibility or compliance needs a decision before implementation.
- **Not planned:** excluded from the proposed lightweight manager scope, unless explicitly reprioritized later.

P0 means a security/compliance/correctness gate; P1 means core usable-client work; P2 is later client functionality; P3 is optional scope. Native interactions in the matrix are design proposals inferred from the public references and macOS controls, not observations of a logged-in official application. All mutation tests must mock Telegram; no automated test may send real messages.

Pre-V3 implementation evidence: [IPC contract](IPC.md), [chat API](CHAT_API.md), [account isolation](MULTI_ACCOUNT.md), [architecture](ARCHITECTURE.md), [UI validation](UI_VALIDATION.md); source modules `ipc.py`, `accounts.py`, `chat_features.py`, `chat_store.py`, `telegram.py`, `storage.py`, and the Swift `AppModel`/native views. Cached pages, explicit bounded reads and confirmed sends are implemented. A general real-time Telegram client, cloud-draft synchronization and a complete rich-message renderer are not.

## Phase 2 gates and test plan

1. **Compliance baseline:** settle unofficial naming/branding, gate unsupported channel-content access, audit ephemeral/protected content, and specify normal read/typing/presence behavior. These must precede broader messaging parity claims.
2. **Capability inventory:** record installed Python, Telethon version/layer and actual public request/type availability. A method on today's online API page is not proof it exists in installed Telethon 1.45.x. New constructor fields must not be guessed or silently ignored.
3. **Reusable backend contract:** keep existing SQLite/session paths, account bindings, generation checks, reservation ledger and strict local IPC. Add typed content/capability/error models rather than moving Telegram requests into Swift.
4. **Client synchronization:** design bounded public update handlers, reconnect/gap recovery, current-peer lifecycle and stable scrolling before adding many actions. Delegate protocol state handling to the supported client library rather than implementing an ad hoc MTProto update engine.
5. **Test boundaries:** unit tests for each row's safety rules; mocked integration tests for account/peer/message/thread binding; actual subprocess framing/cancellation/EOF; native model/state tests; genuine fixture screenshots and keyboard/VoiceOver checks only on an unlocked graphical Mac.
6. **Live acceptance:** remains a separate user-controlled activity. No test may log into the user's account or send/edit/delete/forward/react/download private content merely to make the matrix green.

The current managed environment has compiled native targets and executed offline model/transport tests, but graphical XCUITest has been blocked by `com.apple.testmanagerd.control` sandbox error 159. See [UI validation](UI_VALIDATION.md) for exact attempts. Source inspection and fixture tests cannot establish pixel-level similarity, live behavior, full functionality parity, or distribution readiness.

This research intentionally makes no implementation changes. Update each row with the implementing files, exact mocked/native/live evidence and remaining limitations only after its code and relevant tests exist.

## M2 implementation delta: mocked security evidence

The matrix above remains the pre-V3 research baseline. M2 now adds `content_policy.py`, `message_projection.py` and `update_pipeline.py`, integrated through the existing strict IPC router and runtime Telethon client. This is a bounded client projection, not full Telegram parity or a replacement for Telethon's MTProto update-state handling.

- Supported cached peer kinds are verified before history/media/personal-send access. Broadcast channels and bots remain gated while sponsored-message support is absent. Restricted/protected/unknown peers are unavailable. Cached legacy rows lacking known policy state expose no message preview.
- Typed supported messages retain Unicode text and available reply/reaction/read metadata. Unknown constructors/media, restrictions, protected messages and disappearing media produce unavailable placeholders without body/media export. History, single-message retrieval and reply targets verify actual returned peer/message identity.
- Runtime new/edit/delete/read/typing projection is scope-frozen to account, profile generation and client instance. It uses a bounded 256-entry ingress queue and 200-message window. Tombstones, duplicate suppression, monotonic read boundaries and stale-edit rejection protect the active projection. Ambiguous deletion or overflow requires resynchronization; a full IPC control queue fails the transport rather than silently dropping deletion events.
- Read acknowledgement accepts only supported incoming IDs actually returned for the watched conversation. This is a backend eligibility bound, not proof that a row was physically visible. Swift viewport/focus integration must independently establish actual visibility. Loading a page must not imply reading every row or typing into a hydrated draft.
- Runtime stop removes handlers, cancels the worker and clears private projected message/read state. Cached conversation metadata and the persistent delivery ledger retain their existing account isolation and preservation rules. A peer snapshot does not certify that every cached conversation is fresh.

Independent adversarial evidence: `tests/test_v3_security.py` executed **23 tests and 28 subtests successfully** with synthetic Telethon objects and mocked operations. Cases cover fail-closed projection, channel/bot/restriction gates, no restricted body persistence, wrong-peer history/media/reply, generation/client replacement, read frontiers, ambiguous deletes, overflow, duplicate/old update handling, handler cleanup and transport backpressure. This does not establish genuine UI visibility behavior, live synchronization, sponsored-message compliance, protected-content acceptance on Telegram, or successful real-account operations. Later validation may add tests without changing the scope of this evidence.

## M3 implementation delta: narrowly scoped own-text actions

`conversation_actions.py` adds expiring one-use previews and exact confirmation for editing or deleting one verified own plain-text personal/Saved Messages message. It re-fetches and verifies actual peer/message identity, authorship and unchanged contents at commit. Rich/formatted/media/forwarded/bot/channel/managed-group targets remain unavailable. Deletion is **for the current account only**, using `revoke=False`; deleting another participant's copy is not implemented.

The additive `conversation_operations` table records account/peer/message/action/digest, durable reservation and acknowledged/rejected/uncertain result without storing message bodies. Its required unique reservation index is validated. It does not repurpose or erase the existing send ledger. Cancellation or transport failure after reservation remains uncertain; reopening the database does not permit repeating that exact reserved action. This conservative duplicate rule also applies to recorded rejected operations; there is no automatic retry workflow.

Independent `tests/test_v3_actions_security.py`: **14 tests and 31 subtests passed**, using synthetic TL messages and mocked network only. Coverage includes outgoing-flag ownership spoofing, wrong peer/ID, unsupported content/destination gates, token account/profile/generation/expiry/kind, exact single-use confirmation, changed-target conflict, delete-for-me scope, cancellation/transport uncertainty, restart-persistent duplicates, FloodWait persistence, schema uniqueness, body-free account-isolated history and unchanged send-ledger records. Live Telegram editing/deletion and the native action dialogs require their separate acceptance evidence; these tests do not establish them. Forwarding, reaction mutation, pinning, scheduled sends and delete-for-everyone remain unsupported.

## M4 implementation delta: explicit read-only people/folders and image previews

`client_features.py` adds explicit contact refresh, bounded cached contact search/pages, cached-contact opening and cached/own-peer profile reads. Contact membership comes from Telegram's contact vector, not every user included in a response. Telegram's contact RPC has no request limit: the server response may be larger, while the application's derived projection is capped at 1,000 contacts and reports truncation. Per-account DTO/cache allowlists omit phone numbers, access hashes, session data and arbitrary raw objects; profile/full-object identity is checked before returning details. Unknown member counts remain unknown. An incomplete refresh preserves the previous snapshot.

Telegram folder definitions are read-only metadata with public peer IDs and an explicit `membership_supported:false` marker. This is not folder editing or full Telegram folder-membership filtering, and it is not a renamed local-label feature. Avatar retrieval remains unsupported; `has_photo` metadata is not an image cache or verified identity.

`media_preview.py` supports an explicitly selected normal JPEG/PNG attachment only, with verified account/peer/message identity and existing protected/TTL/bot/channel gates. Compressed size is at most 8 MiB per file, with four cached files (at most 32 MiB). Files are private, generated paths; an index records only their generated basename and device/inode identity. Crash recovery removes only matching recorded owned files; an unknown/replaced matching filename is preserved and blocks more previews rather than authorizing a broad sweep. Release, close and invalidation clean owned preview data. Backend expiry is **lazy**: expired entries are purged on cache access, with close/release cleanup; this is not an absolute idle-time or secure-erasure guarantee. Native decoding, source-dimension limits, downsampling and UI lifetime handling require their separate Swift evidence.
